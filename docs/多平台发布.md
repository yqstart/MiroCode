# 多平台发布（GitHub Actions）

本机只有 macOS 时，用 Actions 云端分别构建 macOS / Windows / Linux，并上传到 GitHub Release。

工作流文件：`.github/workflows/release.yml`（基于官方 [tauri-action](https://github.com/tauri-apps/tauri-action)）。

## 构建矩阵

| Runner | 产物目标 |
|---|---|
| `macos-latest`（Apple Silicon） | 原生 arm64 → `.dmg` + updater `.app.tar.gz` |
| `macos-15-intel`（Intel） | 原生 x86_64 → `.dmg`（勿在 ARM 上交叉编译，会缺 OpenSSL） |
| `ubuntu-22.04` | Linux x64 → `.deb` / `.AppImage` 等 |
| `windows-latest` | Windows x64 → `.msi` / `.exe` 等 |

当前**不做** Apple 公证与 Windows 代码签名（可后置到仓库 Secrets）。  
macOS 构建已启用 **ad-hoc 签名**（`bundle.macOS.signingIdentity: "-"`），避免从 GitHub 下载后在 Apple Silicon 上出现「已损坏，无法打开」；首次打开仍可能需在「隐私与安全性」中允许，或右键 → **打开**。  
应用内更新依赖 **Tauri updater 签名**（与系统代码签名无关，见下文）。

### macOS：安装后提示「已损坏，无法打开」

这是 Gatekeeper 对未公证包的误报，并非安装包真的坏了。

**已安装当前版本**，在终端执行（路径按实际安装位置改）：

```bash
xattr -cr "/Applications/Miro Code.app"
```

然后正常双击打开；若仍拦截，右键应用 → **打开** → 确认一次即可。

**从源码本机构建**时同样已在 `tauri.conf.json` 写入 ad-hoc 签名；发新版 Release 后新下载的 `.dmg` 一般不再出现「已损坏」。

### Windows：SmartScreen 提示「已保护你的电脑」

浏览器从 GitHub Release 下载的安装包（`.msi` / `.exe`）未做 **Authenticode 代码签名** 时，Windows Defender SmartScreen 会提示「已保护你的电脑」或「无法验证发布者」，这是预期行为，**不是安装包损坏或含病毒**。

#### 用户侧：继续安装（当前未签名版本）

任选其一即可：

1. **安装程序界面**：点 **更多信息** → **仍要运行**
2. **解除下载标记**（PowerShell，路径按实际下载位置改）：

```powershell
Unblock-File -LiteralPath "$env:USERPROFILE\Downloads\Miro Code_*.msi"
```

或对 `.exe` 安装包执行同样命令。然后再双击安装。

3. **文件属性**：右键安装包 → **属性** → 勾选 **解除锁定** → 确定 → 再运行

#### 维护者侧：彻底消除提示（需代码签名证书）

Windows **没有** macOS ad-hoc 签名这种免费方案；要双击即装、无 SmartScreen 拦截，必须对 `.exe` / `.msi` 做 Authenticode 签名。

本仓库 Release 工作流已支持**可选**签名：在 GitHub Secrets 配置以下三项后，Windows job 会自动导入证书并签名：

| Secret 名 | 值 |
|---|---|
| `WINDOWS_CERTIFICATE` | `.pfx` 证书的 Base64（Windows：`certutil -encode cert.pfx base64.txt`，取 txt 正文） |
| `WINDOWS_CERTIFICATE_PASSWORD` | 导出 `.pfx` 时设置的密码 |
| `WINDOWS_CERTIFICATE_THUMBPRINT` | 可选；证书指纹（SHA1）。留空时 CI 从刚导入的证书自动读取 |

证书来源可选：

- 商业 **OV / EV 代码签名证书**（DigiCert、Sectigo 等）
- **Azure Trusted Signing**（云签名，适合 CI，见 [Tauri Windows 签名文档](https://v2.tauri.app/distribute/sign/windows/)）

`tauri.conf.json` 已设置 `bundle.publisher: "Miro Code"`，签名后安装界面会显示正确发布者名称。

## 应用内自动更新

客户端通过 `tauri-plugin-updater` 拉取：

`https://github.com/yqstart/MiroCode/releases/latest/download/latest.json`

| 行为 | 说明 |
|---|---|
| 启动自动检查 | 设置 → 关于 →「启动时自动检查」（默认开）；启动约 4 秒后静默查 |
| 手动检查 | 设置 → 关于 →「检查更新」 |
| 安装 | 用户确认后下载签名包、校验公钥、安装并重启 |

### 发版前必配：更新签名密钥（只需一次）

私钥保存在本机（**勿提交仓库**）：`.secrets/mirocode.key`  
公钥写入 `src-tauri/tauri.conf.json` → `plugins.updater.pubkey`（**公私钥必须成对**；换私钥后务必同步改公钥并提交）。

常见「密钥错误 / A public key has been found…」原因：
- Secret 里贴了公钥或截断内容 → 应贴 `.secrets/mirocode.key` **全文**
- 仓库里 `pubkey` 与 Secret 私钥不是同一对
- `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` 与生成时密码不一致（当前为空）

在 GitHub 仓库配置 Secrets（Settings → Secrets and variables → Actions）：

| Secret 名 | 值 |
|---|---|
| `TAURI_SIGNING_PRIVATE_KEY` | `.secrets/mirocode.key` **全文**（含换行） |
| `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` | 空字符串即可（生成时未设密码） |

本机可用 CLI 写入（在仓库根目录）：

```bash
gh secret set TAURI_SIGNING_PRIVATE_KEY < .secrets/mirocode.key
gh secret set TAURI_SIGNING_PRIVATE_KEY_PASSWORD --body ""
```

> 丢失私钥后，已安装用户将无法再通过应用内通道升级，只能重装。请备份 `.secrets/mirocode.key` 到密码管理器。

Release 产物会包含 `latest.json` 与各平台 `.sig`；未配置上述 Secrets 时，开启 `createUpdaterArtifacts` 的构建会失败。

## 发版步骤

### 方式 A：打版本标签（推荐）

1. 确认 `package.json`、`src-tauri/tauri.conf.json`、`src-tauri/Cargo.toml` 的 `version` 一致（当前基线 `0.11.0`）
2. **同步更新 `CHANGELOG.md`**：把 `[Unreleased]` 下条目挪到新版本节（含日期），并更新文末版本对比链接；未写入变更日志不得发版（Release 正文与应用内「新功能」均由该节生成，可用 `node scripts/release-notes.mjs` 预览）
3. 提交并推送到 `master`
4. 打标签并推送（版本号替换为实际值，如 `v0.10.2`）：

```bash
git tag v0.10.2
git push origin v0.10.2
```

5. 打开仓库 **Actions -> Release**，等待 4 个 job 全绿
6. 打开 **Releases**，对应 `v0.10.2` 下应出现各平台 Assets，以及 `latest.json`

标签名须为 `v` + 配置里的版本号（工作流使用 `v__VERSION__`，`__VERSION__` 由 `tauri.conf.json` 填充）。

### 方式 B：手动触发（给已有 Release 补包）

例如已有手建的 `v0.1.0`、缺安装包：

1. 确认当前 `master` 上 `tauri.conf.json` 的 `version` 仍是 `0.1.0`（与 tag 一致）
2. **Actions → Release → Run workflow**
3. 跑完后 Assets 会挂到已有 `v0.1.0` Release

若手动触发时配置版本已改成更新版本（如 `0.10.2`），会去找/创建 `v0.10.2`，而不是补上一版本。

## 仓库权限（必查一次）

**Settings → Actions → General → Workflow permissions**

- 勾选 **Read and write permissions**
- 保存

否则 `tauri-action` 上传 Release 会报 `Resource not accessible by integration`。

## 语言服务捆绑包发布（独立于应用发版）

内置语言服务（Node + `typescript-language-server` + `@vue/language-server`）由**独立工作流** `.github/workflows/language-servers.yml` 打包发布，不随主应用版本走：

- 产物：5 平台（darwin-arm64 / darwin-x64 / win32-x64 / linux-x64 / linux-arm64）`language-servers-<版本>-<平台>.zip`（含便携 Node，约 60MB）+ 版本清单 `ls-latest.json`
- 发布位置：GitHub Release 固定 tag **`language-servers`**（每次发布覆盖更新），应用内「设置 → 编辑器 → 语言服务 → 一键安装」通过 `releases/latest/download/language-servers/ls-latest.json` 拉取
- 国内访问：应用端默认「自动」模式先走 GitHub 官方，失败自动切换 `ghfast.top` 加速镜像（前缀与官方同构）

### 发布步骤

1. 更新语言服务依赖版本（当前捆绑 `typescript@^5.9` + 最新 `typescript-language-server` / `@vue/language-server`），可先本机跑 `node scripts/language-servers/build.mjs --platform <本机平台> --version <版本>` 冒烟验证（产物解压后 `node/bin/node` 直接启动 server 应能完成 LSP initialize 握手）
2. **Actions → Language Services → Run workflow**，填入版本号（如 `0.2.0`）
3. 等待 5 个 build job + publish job 全绿；Releases 页 `language-servers` 下应出现 5 个 zip + `ls-latest.json`

> 版本号独立递增，与主应用版本无关；应用内「更新语言服务」按钮检测到版本不一致即可一键升级，无需重装应用。
